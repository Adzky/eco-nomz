## 1. Project Overview

### 1.1 Background

Food waste is a significant challenge for restaurants, bakeries, cafes, and other food businesses. At the same time, many consumers seek affordable meals.

Eco-Nomz aims to connect food businesses that have surplus food with consumers who want to purchase it at a discount before it goes to waste. Restaurant owners can publish surplus-food offers, customers can discover nearby offers, and customers can reserve and collect food during specified pickup windows.

The initial implementation will focus on a web-based minimum viable product (MVP) for the Indonesian market.

### 1.2 Project Objectives

- Reduce avoidable food waste by connecting businesses with consumers.
- Help food businesses recover revenue from surplus food.
- Provide customers with affordable food options.
- Build a secure, maintainable, and scalable web application.
- Validate the business model through a small pilot involving local food businesses.
- Develop a product that can be demonstrated and evaluated during the NextDev incubator program.

### 1.3 Target Users

#### Customers

- Browse available food offers.
- View discounted prices and pickup information.
- Reserve food.
- View order status and pickup details.

#### Restaurant Owners

- Manage restaurant information.
- Create and update food offers.
- Set available quantities and pickup windows.
- Manage reservations and confirm food collection.

#### Administrators

- Manage user accounts and restaurant listings.
- Review reported listings.
- Monitor orders and platform activity.

### 1.4 MVP Scope

The first release will include:

- User registration and authentication.
- Role-based authorization.
- Restaurant profiles.
- Food offer management.
- Food offer discovery and filtering.
- Order reservations and inventory management.
- Order status tracking.
- Pickup verification.
- Basic administrative functionality.

The following features are deferred until after the MVP:

- Native Android and iOS applications.
- Complex recommendation algorithms.
- Multiple payment providers.
- Loyalty programs and subscriptions.
- Microservices architecture.
- Advanced analytics and machine learning.

## 3. Architecture and Design Principles

### 3.1 Architecture

The MVP will use a modular monolithic architecture. The application will run as a single Spring Boot application, with clear boundaries between authentication, users, restaurants, offers, orders, payments, and administration.

The request flow will be:

1. The browser sends an HTTP request.
2. Spring Security applies authentication and authorization rules.
3. Spring MVC routes the request to the appropriate controller.
4. The controller delegates business operations to a service.
5. The service accesses repositories through Spring Data JPA.
6. PostgreSQL stores or retrieves the data.
7. Thymeleaf renders the resulting HTML page.

### 3.2 Architectural Principles

- Keep business logic inside service classes.
- Keep controllers focused on HTTP requests and responses.
- Use repositories for persistence operations.
- Use DTOs to separate external request and response models from database entities where appropriate.
- Enforce authorization on the server, not only in the interface.
- Use database transactions for operations that modify inventory and orders.
- Keep secrets and credentials outside source control.
- Build the MVP before introducing unnecessary infrastructure.

### 3.3 JWT and Thymeleaf Authentication Strategy

JWT will be used to satisfy the authentication requirement. Because Thymeleaf is server-rendered, authentication must be integrated with browser navigation rather than treated as a standalone mobile API.

The planned approach is:

- Authenticate users using Spring Security.
- Generate a signed JWT after successful authentication.
- Store the token in an `HttpOnly`, `Secure` cookie in production.
- Validate the token through a Spring Security filter for protected requests.
- Load or resolve the user's identity and authorities.
- Enforce role-based access for customer, restaurant-owner, and administrator routes.
- Implement logout by clearing the authentication cookie and following the chosen token-expiration and revocation policy.

Cookie-based JWT authentication still requires CSRF protection for state-changing requests. Do not disable CSRF protection indiscriminately.

Passwords must be stored using a strong password-hashing algorithm through Spring Security, such as BCrypt. Before deployment, test token expiration, cookie security, logout behavior, and unauthorized access handling.

### Phase 7 — Pickup Verification and Payment Integration

**Goal:** Complete the food reservation lifecycle.

**Tasks**

- [x] Generate a unique, unpredictable pickup code.
- [x] Show pickup instructions on the customer's order page.
- [x] Allow authorized restaurant owners to verify pickup codes.
- [x] Ensure a pickup code can only be redeemed once.
- [x] Define payment and cancellation policies.
- [x] Select Midtrans Snap for the Sandbox payment integration.
- [x] Integrate the Sandbox checkout flow; no real funds are moved.
- [x] Verify Midtrans notification signatures and match merchant order, amount, and currency.
- [x] Make duplicate webhook processing idempotent under database row locks.
- [x] Handle provider payment failure and expiration, releasing inventory.
- [x] Add payment checkout and webhook unit tests; PostgreSQL-backed lifecycle coverage remains Docker-dependent.

**Sandbox payment and cancellation policy**

- Midtrans checkout expires 15 minutes after reservation. A 2-minute server-side grace period allows the provider's final notification to arrive before fallback inventory release.
- Checkout uses Midtrans Snap Sandbox. Sandbox is for testing and does not move real funds.
- Customers may cancel only before opening checkout; once a Midtrans checkout exists, they must cancel at Midtrans or let it expire. Paid transactions cannot be cancelled in-app because real refunds are not implemented.
- A payment notification received after a reservation is already expired is marked `REVIEW_REQUIRED` and must be reconciled in Midtrans MAP; the order is not confirmed or restocked twice.
- Production credentials, production URLs, and real refunds are not implemented.

**Deliverables**

- Pickup verification.
- Completed order workflow.
- Midtrans Snap Sandbox checkout and signature-verified payment notifications.

**Acceptance criteria**

- Pickup codes cannot be reused.
- Only authorized restaurant staff can confirm collection.
- Only verified Midtrans notifications can confirm an order.
- Duplicate webhook deliveries do not repeat order or inventory transitions.

Configure `MIDTRANS_SERVER_KEY` and `MIDTRANS_CLIENT_KEY` as local environment variables. The notification endpoint is `/payments/midtrans/notifications`; set the Midtrans MAP Payment Notification URL to `https://<public-tunnel-host>/payments/midtrans/notifications`. Set `MIDTRANS_PUBLIC_BASE_URL` to the same public origin so checkout returns to the application. Do not enable production payments until production credentials, HTTPS hosting, reconciliation, and refunds are implemented and tested.

## 9. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Inventory overselling | Use atomic stock updates, transactions, and concurrency tests. |
| Unauthorized data access | Enforce server-side authorization and ownership checks. |
| JWT theft or misuse | Use short token lifetimes, secure cookie handling, and a rotation or revocation strategy where appropriate. |
| Food offers remaining available after pickup windows | Validate availability and implement scheduled or on-demand expiration. |
| Payment discrepancies | Verify webhooks and use idempotent processing. |
| Insufficient restaurant adoption | Start with a small local pilot and validate business needs. |
| Scope becoming too large | Prioritize the MVP and defer advanced features. |
| Unverified environmental claims | Measure outcomes and document the methodology. |
